Overhead Cable Animal Deterrent Build Plan v1

Passive carriage on a powered twine loop. One DC motor, limit-switch reversal, ESP32 trigger. Companion to the rabbit-detector camera + server system.

Concept in one line: a fixed DC motor drives a continuous loop of fishing line strung between two metal posts. A light, dumb (passive) carriage hangs on the loop. On a rabbit detection, the server tells the ESP32 to run the motor; the carriage shuttles end to end, and limit switches flip the motor direction at each post. Overhead motion + a hawk-silhouette/streamer mimics an aerial predator.

1. How it works

  1. Idle: ESP32 sleeps with WiFi associated, listening for a trigger from the server.
  2. Trigger: server detection loop hits ALERT → sends a message (HTTP/MQTT/ESP-NOW) → ESP32 wakes.
  3. Run: ESP32 drives the H-bridge, motor pulls the loop, carriage travels toward the far post.
  4. Reverse: carriage trips the far limit switch → ESP32 reverses motor direction → carriage returns.
  5. Stop: carriage trips the home limit switch → ESP32 stops the motor → back to idle. Repeat for N passes per alert if desired.

Because motion is constrained to one dimension, there is no obstacle avoidance, no localization, and no docking problem. "Home" is just the home-end limit switch.

2. Mechanical layout

  • Posts: metal, driven into the dirt. Add a guy-line or a deadman anchor if the span is long; loop tension pulls the post tops toward each other.
  • Loop: braided fishing line or twine in a closed loop around two pulleys. Braided line resists stretch better than mono; twine is grippier on the drive pulley.
  • Drive pulley: 3D-printed, on the motor shaft. Add a rubber band / TPU tire or a V-groove so the line does not slip.
  • Tension: make the idler pulley position adjustable (slot + bolt) so you can take up slack. A spring-loaded idler keeps tension as the line stretches and temperature changes.
  • Carriage: clamps to one run of the loop so it moves with the line. Keep it light to reduce sag and motor load.

TB6612FNG quick facts. Dual H-bridge, so two motor channels (A and B). You only need channel A for one motor. Each channel handles 1.2A continuous, 3.2A peak. Control per channel is 3 lines: AIN1, AIN2 (direction) and PWMA (speed/enable). A shared STBY pin must be HIGH to enable the chip at all. Two supplies: VM = motor voltage (your LiPo), VCC = logic (3.3V from the Feather).
Current headroom. 1.2A continuous per channel is modest. If your motor's running current is near or above ~1A, parallel the two channels: tie AIN1+BIN1, AIN2+BIN2, PWMA+PWMB, and join AO1+BO1 and AO2+BO2. That roughly doubles capacity to ~2.4A continuous / 6.4A peak. Otherwise pick a low-current motor and add a firmware stall timeout (the sketch has one).

Pin choice notes. Avoid ESP32 strapping pins for outputs (GPIO0, 2, 5, 12, 15) — a driver input pulling them at boot can stop the ESP32 from starting. GPIO21/27/33/14/32 above are all safe general-purpose pins on the HUZZAH32. GPIO34/35/36/39 are input-only and have no internal pull-ups, so they are wrong for the limit switches unless you add external pull-up resistors. Add a 0.1µF cap across each switch or debounce in firmware.

6. LiPo sizing the calc you asked for

Two loads: the ESP32 sitting idle 24/7, and the motor running in short bursts on each detection. The surprise is that the ESP32's idle current dominates the daily budget, not the motor, exactly like the main rig. Your battery size is decided mostly by which ESP32 sleep mode you use.

Formula

daily_mAh = I_idle(mA) × 24
          + N × I_motor(mA) × (t_run / 3600)

battery_mAh = daily_mAh × days / DoD     (DoD = usable fraction, use 0.8)

Motor energy is then fixed at 20 × 1000 × (30/3600) ≈ 167 mAh/day. The ESP32 idle term is what swings the result:

Recommendation: use light sleep with WiFi kept associated. Idle drops to ~2mA, the board still wakes on an incoming packet within a DTIM interval (sub-second), and a 2000 mAh 1S LiPo gives ~7 days — matching the main camera rig's recharge cadence. If you can run a trigger wire from the Pi/server side to a Feather GPIO, deep-sleep + ext-wake is even better, but then the motor burst becomes the dominant load and there's little gained over light sleep. Always-on WiFi is a non-starter outdoors: a week needs a ~40Ah pack.
Two things the daily-mAh number does NOT cover — size for these separately:
  • Peak / stall current. At startup and if the carriage jams, the motor pulls its stall current (often several A, much higher than running). This is where the TB6612 bites: a single channel is only 1.2A continuous / 3.2A peak. If stall exceeds that, parallel both channels (section 3) or pick a smaller motor. The LiPo's burst C-rating must also clear stall: a 2000mAh pack at 1A is 0.5C (easy), at 6A it's 3C (check the cell). The firmware stall timeout cuts the motor before the driver overheats.
  • Recharge path. The Feather charges the LiPo over USB at 100mA default (raise to ~500mA with the charge-rate resistor mod). To run truly unattended, feed USB from a small solar panel + charge controller, or swap packs.

Plug in your real motor

Once you measure the motor's running current and your actual cable length (which sets t_run), redo just the motor term. Example: a longer 25 m span at ~1 m/s is ~50 s round trip; at 1.5 A that's 20 × 1500 × (50/3600) ≈ 417 mAh/day for the motor. Add to the idle term for your chosen sleep mode, then ×days ÷0.8.

7. Firmware sketch (ESP32 / Arduino)

const int AIN1 = 21, AIN2 = 27, PWMA = 33, STBY = 13;  // TB6612 channel A
const int LIM_HOME = 14, LIM_FAR = 32;                  // limit switches (NO to GND)
const int PASSES   = 4;                                  // shuttles per alert

void setup() {
  pinMode(AIN1, OUTPUT); pinMode(AIN2, OUTPUT);
  pinMode(PWMA, OUTPUT); pinMode(STBY, OUTPUT);
  pinMode(LIM_HOME, INPUT_PULLUP);
  pinMode(LIM_FAR,  INPUT_PULLUP);
  motorStop();
  // connect WiFi, subscribe to trigger (MQTT topic / HTTP endpoint / ESP-NOW)
}

void driveUntil(int limitPin, bool forward) {
  forward ? motorFwd() : motorRev();
  unsigned long t0 = millis();
  while (digitalRead(limitPin) == HIGH) {     // HIGH = not pressed (pull-up)
    if (millis() - t0 > 8000) break;          // stall timeout, protects motor
    delay(5);
  }
  motorStop();
}

void runDeterrent() {
  for (int i = 0; i < PASSES; i++) {
    driveUntil(LIM_FAR,  true);               // out to far post
    driveUntil(LIM_HOME, false);              // back home
  }
}

// TB6612: STBY must be HIGH to drive; PWMA sets speed (HIGH = full).
void motorFwd()  { digitalWrite(STBY, HIGH); digitalWrite(AIN1, HIGH); digitalWrite(AIN2, LOW);  digitalWrite(PWMA, HIGH); }
void motorRev()  { digitalWrite(STBY, HIGH); digitalWrite(AIN1, LOW);  digitalWrite(AIN2, HIGH); digitalWrite(PWMA, HIGH); }
void motorStop() { digitalWrite(PWMA, LOW);  digitalWrite(AIN1, LOW);  digitalWrite(AIN2, LOW);  digitalWrite(STBY, LOW); }

Pulling STBY LOW in motorStop() drops the driver into standby (~µA) between alerts. Use ledcWrite on PWMA if you want speed control instead of full-on. Add debouncing on the limit reads and enter light sleep between alerts.

8. Server integration

The detection already exists. On the server side, when the state machine transitions to ALERT, publish a trigger the ESP32 is listening for. Cleanest option for an intermittent listener is MQTT (broker on the A6000 cluster, ESP32 subscribes), or ESP-NOW if a second ESP32 sits next to the server. Reuse the same ALERT hook you'd use for any deterrent action.

9. Build order

  1. Bench test the drive. Motor + driver + ESP32 on a short loop on the desk. Confirm direction control and limit-switch reversal before going outside.
  2. Measure motor current (running + stall) and finalize battery capacity from section 6.
  3. Rig the cable. Posts, pulleys, tensioned loop, carriage. Verify it shuttles smoothly by hand, then under power.
  4. Mount limit switches at both posts; tune trip positions.
  5. Trigger integration. Wire the server ALERT → ESP32. End to end test with a real detection.
  6. Weatherproof the home-post electronics box, switch to PETG/ASA prints, add the solar/USB recharge path.

Open question to close out: measure the motor's running and stall current. That sets the final battery capacity (section 6) and decides whether one TB6612 channel is enough or you need to parallel both.
